Overview

What This Is

The Central Studio Dashboard is a live operations board for the studio's rental/booking business: who needs a call, what's coming up, open website leads, a quick "is business on pace" read, and revenue reporting. It's built from four moving pieces:

  • One Google Sheet is the entire database — bookings, inquiry, and historical tabs. Nothing else stores state.
  • One Apps Script project (CentralStudio_SM) is the JSON API layer the dashboard talks to. See Deployment Notes for its script ID and deployed Web App URL.
  • A second, smaller Apps Script project (CentralStudio_SM_CalendarSync) is a one-way bridge that copies Chris Connelly's personal-calendar studio bookings into the same Sheet — see Chris Connelly.
  • A static HTML/CSS/JS front end (web/: index.html, app.js, styles.css) hosted on Ionos, calling the main Apps Script's deployed Web App URL via fetch().
No logins. Nothing here has a password or PIN — access is "know the URL." Don't post the link publicly.

Key Concepts

  • The Sheet is the single source of truth. The dashboard never caches anything server-side — every load reads the live tabs fresh.
  • Columns are matched by header name, not position (readRows_ in Code.js). Reordering columns on the sheet is safe; renaming a header the code depends on will break whatever reads it.
  • Every API response has the same shape: { ok: true, data: ... } or { ok: false, error: "message" }. Reads are GET ?action=X; writes are POST with a JSON body { action: X, ... }.
  • Chris Connelly is special-cased throughout. He books via his personal Google Calendar instead of the Calendly form everyone else uses, and several behaviors are hard-coded around his email, chris@chrisconnellyphotography.com (the CHRIS_AUTO_SYNC_EMAIL constant). See Chris Connelly.
  • Two separate things have to be deployed independently — the Apps Script backend and the static frontend. Neither deploy step touches the other. See Deployment Notes — this has bitten us more than once.
Live Dashboard

Needs a Call

Active (non-cancelled) bookings that don't have a Date Called yet. Each card shows the customer's name, a Regular badge if they've booked more than once before (by email), the rental date/time, when it was booked, and a tap-to-call/text phone link. Expanding a card reveals every remaining intake field (event type, payment terms, group size, lighting needs, notes, etc).

Mark Called stamps Date Called with the current time and moves the booking to Vetted Upcoming Rentals.

Vetted Upcoming Rentals

Called bookings, sorted soonest-first by event date/time. Only the next 5 days show by default (a "Show N more" button reveals the rest without a second fetch — bookings with no parseable event date always sort last, into that "more" bucket).

  • Undo Call clears Date Called, sending the booking back to Needs a Call.
  • Complete & Close opens a modal asking for the final payment amount. Submitting sets Total Paid, which removes the booking from the dashboard entirely — for everyone except Chris (next point).
Chris Connelly is the one exception. His rows get Total Paid pre-filled to $150 automatically the moment the Calendar Sync creates them — before the rental has even happened. If the normal rule applied, he'd vanish from the dashboard immediately. So specifically for his email, "completed" bookings stay visible in Vetted Upcoming Rentals until the event's actual start time passes, then drop off like everyone else's.

A booking only ever leaves the dashboard because Total Paid got set — a past event date alone does not hide it, since past bookings may still need calling or closing out.

Website Inquiries Needing Follow-up

inquiry tab rows where Date Contacted is still blank. Each card shows name/phone/email, desired rental date, and the project description they submitted. Log Contact opens a modal with an optional note (appended with a timestamp — repeat follow-up attempts build a history rather than overwriting each other) and a choice:

  • Close Inquiry — sets Date Contacted, removing it from this list for good.
  • Leave Open for Follow-up — just logs the note/attempt timestamp and keeps it open.
Live Dashboard

Studio Health

A fast "is the business on pace" read, sitting above Revenue. Five tiles, each comparing this month's number against a baseline and scoring it. Backed by getStudioHealth() in Code.js.

The Five Metrics

MetricWhat it countsBaseline
Inquiries This MonthCount of inquiry rows whose Submitted At falls in the current month.Average of this year's completed months (Jan through last month) — never the in-progress current month.
Rentals This MonthCount of active bookings whose Event Date falls in the current month — deliberately the same basis Revenue uses, so "rentals" and "revenue" always agree on what "this month" means.Same year-so-far monthly average approach.
Unique CustomersDistinct customers (by email, falling back to name) among active bookings with an Event Date in the current month.Last month, not a yearly average — correctly looks back across a year boundary in January.
Inquiry → Booking RateOf this month's inquiries, the % whose email or phone also appears on an active booking (any date, not just this month) — see the caveat below.Average of this year's completed months' rates.
Repeat Customer RateOf this month's active bookings (by Event Date), the % from a customer with more than one booking ever (all-time email count).Average of this year's completed months' rates.
Conversion rate is a heuristic, not a real link. There's no shared ID between the inquiry and bookings tabs — a match is "same email or phone shows up in both," not a guaranteed causal relationship. It also structurally understates recent months: a lead from three days ago hasn't necessarily had time to book yet, so mid-month conversion numbers read low until the month has had time to play out. Cancelled bookings never count as a conversion.
Inquiries' baseline can be misleadingly low. It was observed live at 0.0 for a month that already had real inquiries — meaning none of this year's completed months have inquiry rows with a valid Submitted At date. That could mean dated logging only started recently, or that rows get cleared out of the tab after they're closed. Worth checking directly in the sheet before trusting a "Great" rating that's being compared against an artificially-low average.

Tier Thresholds

Every metric is scored the same way — value ÷ baseline — via tierFor_():

RatioTierShown as
≥ 110% of baseline▲ GreatTeal left border, teal status chip

Chris Connelly Sessions

Chris doesn't pay per session — he settles up in blocks of 25. This gauge, sitting between Studio Health and Revenue, tracks that separately from the Total Paid field Revenue reads (which is just the hardcoded $150/session bookkeeping number filled in automatically at sync time — see Calendar Sync). Backed by getChrisPaymentStatus_() in Code.js, and included in every getData response as chrisPaymentStatus.

  • Unpaid Sessions — count of Chris's active (non-cancelled) bookings rows where Session Paid Date is still blank and the Event Date has already passed. Same "is this Chris" rule the revenue category cards use (categorizeBooking_()), so the two never disagree about what counts as one of his sessions. A future booking doesn't count as owed yet, even if unpaid — he hasn't shown up for it. Rows with no parseable Event Date are excluded too, since there's no way to confirm they're in the past.
  • The gauge bar fills 0–25 and visually caps at a full bar once unpaid hits the block size — but the number above it keeps counting past 25, since Chris can keep booking while an invoice is outstanding. A tick mark on the bar flags 15, the usual invoice point.
  • Color tiers: teal under 15, amber 15–24 (invoice territory), red at 25+ (a full block or more owed).
  • Apply Payment — Oldest 25 opens a confirmation modal, then stamps today's date into Session Paid Date on the oldest unpaid, already-happened sessions by Event Date, up to one block of 25 (fewer if less than 25 qualify). Disabled when nothing qualifies.
Requires a one-time setup step. The Session Paid Date column doesn't exist on the bookings tab until setupChrisPaymentColumn() is run once from the Apps Script editor (see One-Time / Manual Utilities). Until then every session reads as unpaid, and clicking Apply Payment will error.

Revenue

Backed by getRevenueStats(). "Revenue" always means Total Paid, summed by Event Date's month — never Date Booked.

Stat Tiles & Tables

  • YTD This Year, Avg / Month (with last year's monthly average as a subvalue), Last Year Total, YTD vs Last Year (dollar diff + %, colored gain/loss).
  • Monthly table: This Year, % of Previous Month, % of Last Year's Average, Last Year, % Change — current month row highlighted.
  • Quarterly table: This Year vs Last Year vs % Change, by quarter.

All of this comes from the historical tab, not live bookings — see that section for why, and for a known small-drift caveat between this and the category cards below.

Revenue by Category

Three cards plus a donut chart, always summing to the same total. Computed live from the bookings tab (not historical) via categorizeBooking_():

CategoryRule
Chris ConnellyInvitee Name equals "Chris Connelly" (trimmed, case-insensitive).
Monster ProductionsEvent Type equals "Monster Productions Shoot" (trimmed, case-insensitive).
Studio RentalsEverything else — the residual bucket.
Can drift slightly from "YTD This Year." The category cards read bookings live; the YTD stat tile reads the frozen historical tab. If a booking's Total Paid gets filled in after its month has already closed out in historical (a late payment logged weeks later, say), the category total for that month will reflect it and the historical YTD figure won't, until someone re-syncs or manually edits historical.

Gross Income Charts

Gross Income — four lines over the current calendar year, all built from data already in getRevenueStats() (no extra backend calls):

  • This Year (solid blue) — stops at the current, in-progress month. Future months are never drawn as a fabricated $0; the frontend nulls out any month past "now" before charting, even if the sheet happens to hold a placeholder $0 row for it.
  • Last Year (dashed gray) — the full prior year, since it's fully closed out.
  • Trend (dotted red) — a linear regression fit to this year's known months only.
  • Last Year Avg (solid green, direct end-label "LY Avg") — flat reference line.

Monthly Gross Since Opening — the full historical tab from the earliest row to the current month (also excludes not-yet-reached months), solid blue actual + dotted blue trend line, with x-axis labels thinned out to whatever fits without overlapping.

Both charts have a hover crosshair + tooltip showing every series' value for that month — nothing is hidden behind hover-only; the same numbers are in the tables above.
Chris Connelly

Calendar Sync

Chris books his own studio time directly on his personal Google Calendar instead of using the Calendly form everyone else goes through. A separate Apps Script project, CentralStudio_SM_CalendarSync, is the bridge — see Deployment Notes for its script ID.

  1. Looks 6 months ahead on Chris's calendar (chris@chrisconnellyphotography.com) every time it runs.
  2. Filters by address, not title — only events whose Location field contains 1095 (the studio's street number) get synced, so his personal appointments are never copied over.
  3. Skips already-synced bookings by matching on the source event's ID (stamped invisibly in the business event's description), not its title — so a booking Chris renamed or moved is still recognized.
  4. Creates a business-calendar event plus one bookings row: Invitee Name = "Chris Connelly", Invitee Email = his address (which also makes the "Regular" badge work automatically), Event Type hardcoded to "4 Hour - Studio Rental", Event Date = the real event start time, Date Called = "N/A" (keeps it out of Needs a Call), Total Paid hardcoded to 150, Booking Status = "Upcoming". If the booking was already synced and Chris later renamed/moved it, the existing business event (and its sheet row's date) are updated instead.
  5. Checks for cancellations hourly. His policy: cancel 72+ hours out and it's really cancelled (event + sheet row deleted); cancel with less notice and he's still billed, so the record is deliberately left alone.
Known constraints: no error alerts if anything fails partway; one-directional only (business calendar is never read back into Chris's calendar); Event Type and the $150 price are both hardcoded regardless of what actually happened; cancellation auto-detection needs a Source Event ID — new syncs always have one, and the older backlog is covered once backfillSourceEventIds() has been run (anything it can't match is handled by the one-time previewChrisOrphanCleanup() / applyChrisOrphanCleanup()); a genuine 72+ hour cancellation permanently deletes the sheet row — unlike a normal Calendly cancellation, there's no "cancelled" record left behind.

historical tab

Two columns: Month (e.g. Aug-26) and Revenue. One row per calendar month — this is what all the top-level Revenue numbers and both Gross Income charts read from, not a live query of bookings.

  • Why it exists: past months are frozen snapshots so they don't silently shift as old bookings data changes, and so the dashboard doesn't have to re-scan every booking ever made on every load.
  • The current month auto-syncs hourly (syncCurrentMonthRevenue_, installed by the one-time setupHistoricalRevenueSync): it recomputes that row's total live from bookings and shows it in italics on the dashboard as a "still moving" flag. Every other row gets reset to normal font.
  • A parsing quirk to know about: a label like Sep-26 gets silently misread by Sheets as "month, day-of-month" (no year) rather than "month, two-digit year," and auto-converted to a Date with some unrelated year. parseHistoricalMonth_() works around this by recovering the real year from the day-of-month digits it lands on instead of trusting getFullYear().
Known Issue

Calendly Timezone Bug

Calendly bookings (everyone except Chris) arrive via a Zap that writes the Calendly start time straight into the sheet without converting it from UTC first. Google Sheets has no way to know the number it's looking at is UTC — it just reads e.g. 18:00:00 as if it were already 6:00 PM America/New_York, when it actually meant 6:00 PM UTC (2:00 PM Eastern during EDT). Every Calendly-sourced Event Date and Date Booked ends up shifted by a fixed few hours. Chris's rows are unaffected — his come from the Calendar API as real timezone-aware instants, never an unconverted string.

The Zap itself still needs fixing. A one-time backfill (below) corrects rows already sitting in the sheet, but it does nothing for new bookings. Add a Formatter by Zapier → Date/Time step between the Calendly trigger and the Google Sheets action that converts the start-time field from UTC to America/New_York, and make sure the Sheets step's Event Date (and Date Booked, if it's also sourced from Calendly) is mapped from that converted output — not the raw Calendly field.

The One-Time Backfill

Code.js has two functions for correcting rows already in the sheet, meant to be run manually from the Apps Script editor:

FunctionWhat it does
previewCalendlyTimezoneFix()Run this first. Logs every change it would make (old time → new time, per row) without writing anything.
applyCalendlyTimezoneFix()Writes the corrected Event Date and Date Booked values. Skips Chris's rows. Refuses to run a second time (guarded by a calendlyTzFixAppliedAt script property) so an accidental re-click can't shift already-corrected rows again.

The correction itself (reinterpretEasternDigitsAsUtc_) reads the wrong stored instant's Eastern wall-clock digits — that's the original UTC value Calendly sent, carried through unconverted — and rebuilds a new instant treating those same digits as UTC. This is DST-safe automatically with no manual 4-vs-5-hour table, because Utilities.formatDate already applies the correct rule for whatever date each row falls on.

How this was diagnosed (worth knowing for the next weird-data report): pasting the live ?action=... URLs directly (bypassing the dashboard/browser entirely) is the fastest way to tell a backend problem from a frontend one. A stuck-on-"Loading…" section with no visible error usually means either the API is erroring (check the raw response) or the browser is holding a stale cached copy of index.html/app.js (hard refresh / incognito rules that out).

A backend change needs two steps, not one. clasp push only updates the project's saved source (HEAD) — it does not move the live /exec URL forward, because that URL is pinned to a specific deployment version. After clasp push, also run clasp deploy -i <deploymentId> against the existing deployment ID, or the dashboard keeps calling old code indefinitely. (Editor-run-only utility functions, like the timezone-fix ones, don't need this — they always run against the latest saved source regardless of what's deployed.)
Adding a new Apps Script service can 403 the whole web app. The deployment runs "as the user who deployed it," and that authorization is scoped to whatever Google services the code used at the time it was authorized. The first time newly-added code calls a service it never called before (this happened with PropertiesService), every doGet/doPost action starts failing with an HTTP 403 until someone manually runs any function once in the Apps Script editor and clicks through the new permission prompt. This affects the whole deployment, not just the function that added the new call — which is why unrelated sections can appear to break at the same time as an unrelated change.
The frontend deploys completely separately. web/index.html, app.js, and styles.css go to Ionos by manual upload — clasp never touches them. Ionos doesn't send Cache-Control headers on these files, so after deploying, a hard refresh (or incognito window) may be needed to see the change; a normal reload can silently reuse a stale cached copy.
